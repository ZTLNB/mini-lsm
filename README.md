# mini-lsm

从零实现的 **LSM-Tree 存储引擎**，纯 Python、零第三方依赖。

这个项目不是把某个现成库包装一下 —— 而是把 LSM-Tree 的每一层
（WAL、内存表、SSTable、Manifest、Compaction、Bloom Filter、Block Cache、
快照隔离、流式迭代器、并发写路径）都手写出来，磁盘格式、CRC 校验、
崩溃恢复语义全部自己定义。目标是把"数据库到底怎么保证数据不丢、
怎么把读放大压下去、怎么在读的同时给出一致视图、怎么让写不必陪着磁盘一起等"
这件事讲清楚。

> **当前进度：阶段 6 / 6 已完成**
> 已有能力：预写日志（WAL）+ 内存有序表（MemTable）+ SSTable 落盘
> + 版本清单（Manifest）+ 分层归并（L0 → L1 → L2，含墓碑清理）
> + 布隆过滤器（Bloom Filter）+ 块缓存（Block Cache）
> + 快照读（一致视图）+ 流式范围扫描 + 崩溃恢复
> + **并发写（三把锁 + 不可变内存表，刷盘/归并的 I/O 全程在锁外）**
> 还没有：per-key 版本链（读历史时间点）、事务、后台维护线程

---

## 为什么值得写这个项目

大多数人理解的"存储"是 `open()` + `write()`。但真实的存储引擎要回答一堆
更难的问题：

- 进程在 `write()` 写到一半时被 `kill -9`，重启后怎么知道哪条数据是完整的？
- 删除一个键，为什么不能真的把它抹掉？那它什么时候才能真的消失？
- 为什么"先把数据写进内存、再写日志"是错的？
- 数据比内存还大时怎么办？重启要把几百 GB 重放一遍吗？
- 磁盘上一个字节被翻转了，怎么发现？
- 文件成批增删到一半崩溃，重启后怎么判断该信哪一套文件？
- 查一个**不存在**的键，为什么还是要把每个文件都读一遍？能不能不读？
- 反复查同一批热点数据，为什么每次都要重新读盘、重新解析？
- 一个加速用的结构（过滤器）自己坏掉了，该不该让整个数据库打不开？
- 一边在遍历、一边有人在写，遍历看到的到底是哪个版本的数据？
- 遍历一个比内存还大的库，为什么不能先把结果全捞出来再返回？
- 一个读操作怎么保证"文件不会被别人删掉"—— 它已经不持锁了？
- 一把锁同时保护"改一个字节的内存"和"写几 MB 的文件"，为什么是坏主意？
- 刷盘的时候，内存表被搬走了 —— 那这段时间新写的数据放哪？读还找得到吗？
- 多个线程同时写，为什么"先写日志、再改内存"必须是**一个**原子步骤？
- 刷完盘为什么不能直接清空日志？（单线程可以，多线程就不行了）

这个项目用约 4900 行 Python 把这些问题逐一解决掉。

## 快速开始

不需要安装任何东西，Python 3.10+ 即可。

```bash
# 跑演示：读写 → 刷盘 → 重启 → 超过内存 → 归并 → 墓碑清理
#          → 过滤器挡掉不存在的键 → 块缓存命中 → 崩溃恢复
#          → 流式扫描 → 快照一致视图 → pin 的磁盘代价
python demo.py

# 跑测试
python -m unittest discover -s tests

# 更重的随机压力测试（和内存字典模型逐步对照，含快照不变量）
python tools/fuzz_compaction.py 80

# 量一下阶段 4 到底省掉了多少次磁盘读
python tools/bench_stage4.py

# 量一下阶段 5 省了多少内存、pin 住多少磁盘
python tools/bench_stage5.py

# 量一下阶段 6：刷盘/归并期间读写到底还会不会被卡住
python tools/bench_stage6.py
```

作为库使用：

```python
import sys
sys.path.insert(0, "src")

from mini_lsm import LSMEngine

with LSMEngine("./mydata") as db:
    db.put("name", "alice")
    db.put("city", "深圳")
    print(db.get_str("name"))        # alice

    db.delete("city")
    print(db.get("city"))            # None

    for key, value in db.scan(b"a", b"z"):     # 流式，内存不随结果集增长
        print(key, value)

    with db.snapshot() as snap:                # 一致视图
        db.put("name", "bob")
        print(snap.get_str("name"))            # alice
```

数据目录里是 `wal.log`、`MANIFEST.json` 和若干 `sst-NNNNNN.sst`。
内存表写满后自动刷成 SSTable，文件攒多了自动归并 —— 所以数据量可以远超内存，
文件数也不会随写入量线性增长。

## 架构

```
                    写入路径（顺序不能反）
    put(k, v) ──► ① 追加到 WAL（落盘，持久性来源）
                    │
                    └─► ② 写入 MemTable（内存，快速生效）
                          ▲
                          └── ①② 必须是一个**原子步骤**（_append_lock）：
                              否则日志顺序和内存表顺序会对不上，
                              崩溃重放出来的状态就和崩溃前不一样。

                              │  满了（默认 4 MiB）
                              ▼
                        ③ 轮转：只换指针（微秒级，_append_lock 里做完）
                              │   满的那张 → 不可变内存表
                              │   新建一张空的接住后续写入
                              ▼
                        ④ flush：把不可变表写成 SSTable（慢 I/O，**不持任何锁**）
                              │   临时文件 + fsync + 原子改名
                              │   ↑ 这段时间其他线程照常写新内存表、照常读
                              ▼
                        ⑤ 更新 MANIFEST（原子替换，短暂持 _state_lock）
                              ▼
                        ⑥ 摘掉不可变表（必须在 ⑤ 之后）
                              ▼
                        ⑦ 重写或截断 WAL（数据已经在新地方了）
                              ▼
                        ⑧ 按需 compaction（L0 → L1 → L2）

                    读取路径（从新到旧，命中即止）
    get(k) ──► 活动 MemTable ──miss──► **不可变 MemTable** ──miss──►
                                    L0 从新到旧逐个试（键范围重叠，没法二分）
                                    │
                                    │  每个文件先问一句：
                                    │  ① key 超出这个文件的键范围？  跳过（免费）
                                    │  ② 布隆过滤器说"一定没有"？    跳过（一次盘都不读）
                                    │  ③ 二分定位到块 → ④ 块缓存在？ 命中就免掉读盘+解析
                                    │  ⑤ 真读那一块
                                    ▼
                                  L1、L2…… 同样的五步，二分先定位到唯一文件
                                    │
                              墓碑也会终止查找

                    范围扫描（流式，不持锁）
    scan() ──► 立刻冻结一个快照（内存表副本 + 层结构副本 + pin 住的文件）
                    │
                    └─► MergingIterator(内存表副本, 快照里的每个文件)
                            → 一条有序流，同 key 取最新，墓碑被过滤掉
                            → 读一块才解析一块（内存不随结果集增长）
                            → 迭代到底 / break / 对象回收 时释放快照
                    （顺序全扫**故意不填缓存** —— 那些块只会被读一次）

                    快照（一致视图）
    快照 = 内存表的有序副本（活动表 + 不可变表合并）+ 那一刻的层结构 + 那一刻的文件集合
        │
        ├─ 之后的写入   → 落进新内存表，副本不受影响
        ├─ 之后的刷盘   → 产生新文件，快照的层结构里没有它
        └─ 之后的归并   → 旧文件被 pin 住，推迟到最后一个快照关闭才删

                    并发控制（三把锁，顺序固定）
    _maintenance_lock ──► _append_lock ──► _state_lock
        │                     │                 │
        │ 串行化刷盘/归并       │ WAL 追加 +       │ manifest / readers /
        │ （manifest 是整体     │ 内存表写入 +     │ 快照表 / 待删清单 /
        │   原子替换，同时改     │ 内存表轮转       │ 计数器
        │   会互相覆盖）        │                 │
        │                     │                 └─ **绝不在磁盘 I/O 期间持有**
        └─ 谁抢到谁干活；抢不到就直接返回，不排队

                    compaction（分层归并）
    L0 文件数到阈值 ──► 整个 L0 + L1 里重叠的文件一起归并 ──► 写回 L1
    L1 超过容量预算 ──► 挑一个 L1 文件 + L2 里重叠的文件归并 ──► 写回 L2
    压到最底层时 ──► 墓碑可以安全丢掉
    旧文件被删掉时 ──► 顺手把它的缓存块清掉（evict_file）
    旧文件被快照引用时 ──► 进待删清单，等最后一个快照关闭再删
    归并的读+写全程在锁外 ──► 所以**读不会被归并卡住**
```

## 磁盘格式

### WAL（`wal.log`）

纯顺序追加，没有索引、没有页结构 —— 因为顺序写是磁盘上最快的操作，
而 WAL 的性能决定了整个写入路径的上限。

每条记录（大端序）：

```
偏移      长度        字段
------    --------    --------------------------------------
0         4           payload_len   —— payload 的字节数
4         4           crc32         —— payload 的 CRC32 校验和
8         1           rec_type      —— 1=PUT, 2=DELETE
9         4           key_len
13        key_len     key
...       4           value_len
...       value_len   value
------    --------    --------------------------------------
合计      8 + payload_len
```

### SSTable（`sst-NNNNNN.sst`）

不可变的有序磁盘表。文件布局（格式版本 2）：

```
+---------------------------+
| 数据块 0                  |   多条 entry，按 key 升序
+---------------------------+   block := [len:4][crc32:4] + entries
| 数据块 1                  |
+---------------------------+
| ...                       |
+---------------------------+
| 索引块                    |   稀疏索引：每块的**起始 key** → (偏移, 长度)
+---------------------------+   同样带 [len:4][crc32:4]
| 过滤器块                  |   布隆过滤器，回答"这个 key 一定不在吗"
+---------------------------+   同样带 [len:4][crc32:4]
| footer（固定 48 字节）    |   索引偏移 + 索引长度 + 条目数
+---------------------------+   + 过滤器偏移 + 过滤器长度 + magic
```

entry 的字节布局和 WAL 的 payload **完全一致**：

```
rec_type(1) + key_len(4) + key + value_len(4) + value
```

两者共用同一套编解码 —— 少一套格式就少一处会写错的地方。

#### 磁盘格式的演进（v1 → v2）

阶段 2/3 写出的文件是 **v1**：32 字节 footer，没有过滤器块。
阶段 4 加了布隆过滤器，footer 变成 48 字节，magic 也从 `MINILSM1` 换成 `MINILSM2`。

**为什么换 magic 而不是加一个版本号字段？** 因为读文件时**必须先知道版本**，
才知道该从末尾往前读多少字节。如果版本号在 footer 内部，就得先假定一个
footer 长度去读它 —— 鸡生蛋。把 magic 放在**最末尾的 8 字节**，
读的时候先读这 8 字节判版本，再按版本解析整个 footer，就没有这个问题：

```
读文件末尾 8 字节
    ├─ "MINILSM2" → footer 是 48 字节，从末尾 -48 开始解析
    └─ "MINILSM1" → footer 是 32 字节，从末尾 -32 开始解析（过滤器偏移/长度记 0）
```

于是**老文件不需要任何转换就能直接打开**。对 v1 文件来说
`might_contain()` 只能返回 `True`（没有过滤器可用），也就是退化成阶段 3 的行为 ——
慢一点，但结果依然正确。

> 加字段可以，但不能让用户已经存下来的数据读不出来。这是磁盘格式演进里
> 最容易被破、后果最严重的一条约束。

### MANIFEST（`MANIFEST.json`）

```json
{
  "version": 1,
  "num_levels": 3,
  "next_file_id": 14,
  "levels": [
    [ {"file_id": 13, "level": 0, "smallest": "azAwMDAw", "largest": "…",
       "entry_count": 61, "size": 5013} ],
    [ {"file_id": 12, "level": 1, "smallest": "…", "largest": "…", …} ],
    []
  ]
}
```

key 是任意字节，JSON 存不下 —— 用 base64 包一层。

## 十个关键设计

### 1. 为什么 `payload_len` 放在最前面？

读取时先拿到长度，才知道后面要读多少字节。这样即使文件被截断，
也能**立刻**判断出"这条记录不完整"，而不是读到一半才发现。
崩溃恢复的正确性直接依赖这一点。

### 2. 为什么 CRC 按块算而不是按条算？

SSTable 的读取粒度就是块 —— 要么整块读进来用，要么根本不读。
按块校验和按条校验能发现的问题一样多，但校验开销只有 1/N。

另外，CRC 能区分两种损坏，这个区分很有用：

- **内容变了但结构还在** → 跳过 CRC 还能读出数据（诊断工具有用）
- **结构已经不可信**（比如长度字段被改）→ 即使跳过 CRC 也只能报截断

后者正是 CRC 存在的意义。

### 3. 为什么是"稀疏"索引？

每 4 KiB 一个索引项，而不是每个 key 一个。索引常驻内存，必须小 ——
1 亿条记录如果逐条建索引，光索引就要好几 GB。稀疏索引让索引大小
正比于"**块的个数**"而不是"记录的个数"，代价是查一个 key 需要在
块内顺序扫一遍（块只有 4 KiB，可以忽略）。

### 4. 为什么用"临时文件 + 原子改名"写 SSTable？

因为"文件名对得上"就等于"内容完整"。崩溃时只会留下一个 `.tmp`，
启动时直接删掉即可 —— 数据还在 WAL 里，不会丢。

**但这个技巧在阶段 3 就不够用了。** 它只能保证"单个文件"的原子性，
而 compaction 要一次性增删**一批**文件。于是有了 Manifest。

### 5. 为什么需要 Manifest？

阶段 2 的文件只增不减，而且文件名和内容一一对应，所以"扫目录"就足以恢复，
简单到几乎没有出错空间。

但 compaction 会**成批**增删文件。崩溃完全可能发生在
"新文件已经写好、旧文件还没删掉"的中间态 —— 这时目录里新旧两套文件
同时存在，光看目录无法判断该用哪一套。**选错就是丢数据。**

Manifest 的解法是**整体原子替换**：把"当前有效的全部文件"写进一个临时文件，
`fsync`，然后 `os.replace`。崩溃后要么看到旧的一套，要么看到新的一套，
不存在中间态。

> 和真实引擎的差别：RocksDB 的 MANIFEST 是**追加式的版本编辑日志**
> （每次 compaction 只追加一条增量记录）。这里每次重写整个文件 ——
> 因为状态只有几 KB，重写的代价可以忽略，而"整体替换"的正确性显然
> 更容易论证。等文件数上万、manifest 变成几 MB 时，才值得换成追加式。

### 6. 为什么 compaction 要带上目标层里"重叠"的文件？

归并的规则是"同 key 只保留最新版本"。如果只把 L0 的文件写进 L1，
L1 里原有的同 key 数据就会和新的并存 —— **层内一旦重叠**，
"二分找到唯一可能包含 key 的文件"这个前提就崩了，查询会静默出错。

所以重叠的文件必须一起参与归并。

### 7. 为什么布隆过滤器的哈希不能用内置 `hash()`？

这是阶段 4 最隐蔽、后果最严重的一个坑。

CPython 对 `bytes` 的 `hash()` 带**每进程随机化**的盐（`PYTHONHASHSEED`，
出于防哈希碰撞攻击的考虑）。而布隆过滤器是**要落盘**的 —— 进程 A 写下的位图，
进程 B 重启后要用同一套位位置去查。如果哈希随进程变化，那么重启之后
所有查询都会落在错误的位上，于是**已经存在的键被报告为不存在** ——
所有数据看起来都"消失"了。

实测（`tests/test_bloom.py::TestCrossProcessStability`，三个子进程用不同的
`PYTHONHASHSEED`）：

```
过滤器字节的 SHA256:  三个进程完全一致  ✅
内置 hash(b"alpha"):  1489347309953176093
                      6606819119385553035
                     -8030786600913837756   ← 三个进程三个值 ❌
```

所以这里用 `hashlib.blake2b`：标准库、跨平台跨版本稳定、分布均匀，
一次调用就能拿到 128 位。

### 8. 为什么过滤器坏了要"降级"，数据块坏了却要"拒绝启动"？

这两个容错策略**故意不同**：

| | 损坏时的行为 | 理由 |
|---|---|---|
| 数据块 | 抛错，拒绝启动 | 读不出数据 = 丢数据 |
| 索引块 | 抛错，拒绝启动 | 索引是"怎么找到数据"的依据，不可信则定位不可信 |
| 过滤器块 | 记一笔，降级成"没有过滤器"，继续打开 | 只影响**快慢**，不影响**对错** |

为了一个坏掉的优化结构而让用户完全打不开数据，是得不偿失的。
降级之后 `might_contain()` 恒返回 `True`，行为退回阶段 3，结果依然正确，
只是多读几次文件。`stats().bloom_corrupt_files` 会把这个情况报出来。

同样的道理，引擎在读路径上**对 `might_contain` 包了一层 try/except** ——
过滤器只要有一次假阴性就是静默丢数据，宁可退回"老实去读"。

### 9. 为什么快照不是"per-key 版本链"，而是"抄一份结构"？

提到 MVCC，第一反应通常是给每条记录编号（`(key, seq)` 的版本链），
查询时带上一个"我能看到的最大序号"。**但那样要改磁盘格式** ——
SSTable 里的 entry 得加字段，WAL 记录得加字段，老文件还得兼容。

这里换了个角度：**SSTable 本来就是不可变的，而 manifest 的每一次替换
就是一个新"版本"**。于是"某一时刻的一致状态"可以精确地表示成三样东西：

```
快照 = 内存表的有序副本 + 那一刻的层结构 + 那一刻的文件集合
```

- **内存表副本**：`list(sorted_items)` 出来的新列表，元素是不可变元组。
  之后的 `put`/`delete` 改的是原 `dict`，碰不到这份副本。
- **层结构副本**：`FileMeta` 是 frozen dataclass，复制一层列表就够了。
  之后 compaction 改的是 manifest 自己的列表。
- **文件集合**：这批文件的 id。它们必须活着 —— 这就是"pin"。

**磁盘格式一个字节都不用改。** 代价是不能读"历史某个时间点"
（没有全局序号），只能读"我自己创建那一刻"—— 而这恰好是
99% 的用法（一次遍历、一次导出、一次备份）。

### 10. 为什么流式迭代期间**不能**持锁？

阶段 4 的 `scan()` 是"锁内把结果物化成 list 再返回"。它有两个毛病：
内存正比于结果集，而且**扫多久就把写阻塞多久**。

改成生成器很自然，但改完之后会立刻撞上一个问题：**迭代期间如果释放锁，
谁保证文件不被 compaction 删掉？**

答案不是锁，而是 **pin**：

```
迭代器持有快照 → 快照 pin 住那批文件 → compaction 只能把它们放进"待删清单"
    → 最后一个引用它的快照关闭时，才真正 unlink
```

于是"读不阻塞写"和"读到的数据一定还在"这两件事可以同时成立。
`tools/bench_stage5.py` 里直接探测了这一点 —— 迭代进行中从另一个线程
`acquire(blocking=False)` 引擎锁，必须是成功的。

顺带一个反直觉的推论：**快照不关，泄漏的是磁盘不是内存。**
被 pin 住的文件在 manifest 里已经不存在了，但物理文件还在。
`bench_stage5.py` 实测：50 个文件被 pin 住时磁盘占用是 491 KiB，
关掉快照后立刻回落到 243 KiB。所以 `with db.snapshot()` 不只是习惯，
是必须。

## 分层归并（Compaction）

### 为什么需要它

阶段 2 结束时有两个明显的问题，`demo.py` 的第 6 节（关掉自动归并跑同一个负载）
里能直接看到：

```
--- 6. 归并省掉了什么:关掉自动归并对同一个负载 ---
  同样 3000 条,但不自动归并: 49 个文件,归并 0 次
    分层: L0=49个/247.1 KiB
    → 查询一个 key,最坏要把 L0 的 49 个文件全翻一遍
```

（同一份负载开着自动归并时是 13 个文件、`L0=1个 L1=12个`。）

**问题一：文件只增不减。** 删掉的键只留下墓碑，文件越攒越多。

**问题二：读放大。** L0 的文件键范围互相重叠，查一个 key 最坏要把
L0 全部翻一遍。实测（`get()` 实际读到的文件数）：

| | 文件数 | 分层 | 每次点查平均读文件 |
|---|---|---|---|
| 不归并 | 49 | L0=49 | **37.1 个** |
| 自动归并 | 13 | L0=1, L1=12 | **1.5 个** |

25 倍的差距。而且这还是 3000 条记录；写入量越大，差距越大 ——
不归并时读成本随写入量**线性增长**，归并后基本是常数。

### 做法

```
L0 文件数到阈值（默认 4）
    ──► 整个 L0 + L1 里键范围重叠的文件一起归并 ──► 写回 L1
L1 超过容量预算（默认 1 MiB，每层 ×4）
    ──► 挑一个 L1 文件 + L2 里重叠的文件归并 ──► 写回 L2
压到最底层时
    ──► 墓碑可以安全丢掉
```

每层的契约不同，这是整层的核心：

- **L0**：由内存表刷盘产生，键范围**允许重叠**，按 `file_id` 从大到小
  表示从新到旧。查一个 key 要挨个试。
- **L1 及以上**：键范围**互不重叠**，按 `smallest` 升序排列。
  于是查一个 key 只需要二分找到唯一可能包含它的文件。
  **这是 compaction 换来的最大收益。**

### 墓碑的归宿

墓碑的作用是压住**更旧**的数据。只要还有更深的层，那层里就可能有
同一个键的旧值，墓碑一丢，旧值立刻复活。

所以规则是：**只有压到最底层才能丢墓碑** —— 此时"不可能再有更旧的数据"
才成立，墓碑才算完成了它的使命。

`demo.py` 里能直接看到效果：

```
--- 10. 墓碑的归宿:压到最底层才真正消失 ---
  写入 a、b、c:磁盘上 3 条
  删除 b:磁盘上 4 条  ← 多了 1 个墓碑
  压到最底层后:磁盘上 2 条
    少掉的 2 条 = 墓碑本身 + 被它压住的 b 的旧值
    存活键: ['a', 'c']
```

### 策略与机制分离

`compaction.py` 只负责**决定该做什么**（策略），真正写文件、改 manifest、
删旧文件是引擎的事（机制）。分开的好处是策略能单独测，不用碰磁盘 ——
各种边界（层超预算、层内重叠、最底层不触发）都能直接构造出来测，
不用真的写几百 MB 数据把某一层撑爆。

### 崩溃安全的总原则

任何改动都遵循同一个顺序：

```
先把新数据落盘（fsync）
    ──► 再原子替换 MANIFEST      ← 从这一刻起，新的一套生效
        ──► 最后删旧数据          ← 此时 manifest 已经不引用它们了
```

崩在任何一步，重启后要么是旧的一套、要么是新的一套，不存在中间态。
崩在最后一步之前会留下"没人引用的文件"—— 它们是**垃圾不是数据**，
因为 manifest 指向的那一套已经是完整的，启动时直接删掉。

## 布隆过滤器与块缓存（阶段 4）

阶段 3 把"查一个 key 要翻几十个文件"变成了"二分定位到 1 个文件"。
但剩下两个开销它解决不了：

- **查一个不存在的键，还是要真读文件** —— 只有读到文件内容，才知道里面没有它
- **反复查热点数据，同一个块被反复读盘、反复解析** —— 而 SSTable 是不可变的，
  解析结果永远不会变

`tools/bench_stage4.py` 把这两笔开销量了出来（关掉块缓存测过滤器，反之亦然）。

### 过滤器省掉了多少读盘

3000 条记录、每组 300 次查询，单位是**每次查询平均读几个数据块**：

| 场景 | 探针 | 无过滤器 | 有过滤器 | 降幅 |
|---|---|---|---|---|
| 顺序写 + 归并（13 文件，L0=1） | 存在的键 | 1.01 | 1.01 | 0% |
| | 范围内不存在的键 | 1.01 | **0.01** | **99%** |
| 顺序写 + 不归并（49 文件） | 存在的键 | 1.16 | 1.15 | 1% |
| | 范围内不存在的键 | 1.15 | **0.16** | **86%** |
| 随机写序 + 不归并（49 文件） | 存在的键 | 21.34 | **1.34** | **94%** |
| | 范围内不存在的键 | 41.85 | **0.52** | **99%** |

过滤器的体积：**合计 3958 字节，占数据体积 1.6%** —— 每 3000 个 key 约 1.3 KB。

### 三个反直觉的发现

**一、"存在的键"也可能被过滤器救一大截。** 上面第三行，查一个存在的键从
21.34 次降到 1.34 次。原因是 L0 按"新到旧"挨个试：这个键躺在比较旧的那个文件里，
于是**所有比它新的文件都要被真读一遍**才能确认"不在这一层"。
过滤器把这些白读全挡掉了。这就是 L0 的读放大。

**二、"key 超出文件键范围"这个检查本身就是一个免费的过滤器。**
对比第二、三行：顺序写时每个文件只覆盖一小段键区间，光靠范围检查
（`key > last_key`，不需要任何磁盘 I/O）就能挡掉大部分文件；
随机写序时每个文件的键范围都接近全域，这个检查失效了，过滤器才顶上。

所以引擎里的顺序是：**范围检查 → 布隆过滤器 → 二分 → 读块**，
最便宜的放最前面。

**三、"范围内不存在的键"比"存在的键"降幅更大。** 前者要试完全部候选文件
才知道"没有"，后者只要找到一个就停。

### 块缓存

缓存的是**解析后的记录列表**而不是原始字节 —— 纯 Python 里逐条解 `struct`
才是真正的开销，命中时能省掉整条"读盘 + 校验 + 解析"路径。

用 `OrderedDict` 实现 LRU（`move_to_end` / `popitem(last=False)`），O(1) 淘汰。
键是 `(file_id, 块下标)`，带 `file_id` 是必须的 —— compaction 之后文件会拿到
**新的**编号（单调递增，绝不复用），不同文件里的"第 3 块"不会互相串味。

```
容量   64 KiB: 冷读命中  97.0%, 热读命中  98.5%, 占用 82.2%
容量  256 KiB: 冷读命中  97.0%, 热读命中  98.5%, 占用 20.5%
容量 1024 KiB: 冷读命中  97.0%, 热读命中  98.5%, 占用  5.1%
```

（冷读命中率不是 0，因为一个块里有多条记录 —— 查第 2 条时就命中了
第 1 条带进来的那一块。）

#### 缓存污染：为什么全扫不填缓存

compaction 和全量 `scan()` 会把整个文件从头读到尾，**每个块只读一次、
之后再也不碰**。如果这些块都塞进 LRU，它们会把真正的热点数据全部挤出去。

所以读取接口带一个 `fill_cache` 开关，默认 `False`：

```python
def iter_entries(self, fill_cache: bool = False):
    ...   # 默认不填缓存;要填得显式说
```

`demo.py` 里能直接看到效果：

```
--- 8. 块缓存:热点数据不重复读盘 ---
  冷读 200 次: 命中 196 / 201 (97.5%)
  热读 200 次: 累计命中 396 / 401 (98.8%)  ← 同一个块不用再读第二遍
  缓存占用: 32.4 KiB / 256.0 KiB (5 块)
  全量 scan() 之后: 命中 0 次, 缓存里仍是 5 块
    —— 这叫缓存污染,所以 scan 默认不填缓存(fill_cache=False)。
```

#### compaction 之后要清缓存

文件被删掉之后，它的缓存块再也不会被读到。不清理**不会读到脏数据**
（`file_id` 不复用），但内存是实打实白占的 —— 而且这种浪费不会报错，
只会悄悄涨。所以 `_apply_compaction()` 里对每个被删的文件调
`block_cache.evict_file(file_id)`。

模糊测试把这条也钉住了：任何时刻缓存里的 `file_id` 都必须是 manifest 里
还活着的文件。

### 布隆过滤器的参数与形状

```
每个 key 分 10 bit（DEFAULT_BITS_PER_KEY）
    └─► 哈希个数 k = 10 × ln2 ≈ 7        ← 这是误判率最低的点
        └─► 位图约一半是 1（bit_density ≈ 0.507）
            └─► 理论误判率 (1 - e^(-kn/m))^k ≈ 0.82%
```

实测（2000 个 key、20000 次探针）：

```
理论误判率 0.8194%   实测 0.8150%   假阴性 0 个
```

1000 个 key 的过滤器总共 **1259 字节**（含 9 字节头部）。

## 快照读与流式扫描（阶段 5）

阶段 4 之后，读路径上还剩两个问题：

- **`scan()` 把结果全部物化成列表** —— 扫一个比内存还大的库，内存会跟着涨；
  而且它是在**锁内**物化的，扫多久就把写阻塞多久
- **读没有一致视图** —— 遍历过程中如果发生刷盘或归并，同一个 key 可能
  被看到两次、也可能被跳过，取决于读到哪一步

`tools/bench_stage5.py` 把这两笔开销和快照的代价都量了出来。

### 流式扫描省了多少内存

12000 条记录（值 96 字节），`tracemalloc` 测**峰值**：

| 做法 | 峰值内存 | 相对 |
|---|---|---|
| `list(db.scan())` ← 阶段 4 | 2.7 MiB | 1.00x |
| 流式，取前 10 条就停 | **73.3 KiB** | **0.03x** |
| 流式，全量遍历但不保留 | **78.3 KiB** | **0.03x** |

内存占用从「正比于结果集」变成「正比于一个块」。结果集再大 100 倍，
后两行的数字也几乎不变。

时间上：取第一个元素 **0.24 ms**，扫完全部 15.8 ms（约 76 万条/秒）。
阶段 4 想拿头几条也得先把整趟跑完。

### 快照读：创建便宜、读起来不额外收费

```
创建 + 关闭一次快照: 52 µs      ← 抄一份内存表 + 抄一份层结构
                                   和文件数成正比，和文件大小无关
创建 20 个快照的峰值内存: 35.5 KiB
```

点查速度（2000 次探针，交替多轮取最小值）：

| 探针 | 实时读 | 快照读 | 比值 |
|---|---|---|---|
| 存在的键 | 13558 µs | 14928 µs | 1.10x |
| 不存在的键 | 5859 µs | 5479 µs | 0.94x |

两条路径共用同一个 `search_levels()`，所以耗时基本一致 ——
快照几乎不额外收费，这是"共用一份读逻辑"换来的。

> ⚠️ 这个对比必须"先各自预热、再交替多轮取最小值"。只测一轮的话，
> **先测的那一方永远吃亏**（块缓存是空的）。我第一版就是这么写的，
> 量出来 1.65x 的差距，全部是预热差异。

### pin 的真实代价：磁盘

| 时刻 | 磁盘占用 | 待删 | 文件数 |
|---|---|---|---|
| compaction 之前 | 1.3 MiB | - | 30 |
| 无快照，compaction 之后 | 1.3 MiB | 0 | 1 |
| **有快照，compaction 之后** | **2.6 MiB** | **30** | 31 |
| 快照关闭之后 | 1.3 MiB | 0 | 1 |

那个快照 pin 住了 30 个文件，多占 1.3 MiB。**这就是"快照必须记得关"
的原因 —— 它不是内存泄漏，是磁盘泄漏。**

### 快照的隔离性是怎么成立的

`snapshot.py` 里的核心是这一段（简化）：

```python
self._mem_keys = [k for k, _ in mem_items]          # 内存表副本
self._mem_values = [v for _, v in mem_items]
self._levels = [list(level) for level in levels]    # 层结构副本
self._file_ids = frozenset(...)                     # 要被 pin 的文件
self._readers = {fid: readers[fid] for fid in self._file_ids}
```

三个细节都是必须的：

1. **层结构必须复制。** 不复制的话，之后 compaction 往 `manifest.levels`
   里增删，快照就跟着变 —— 一致视图立刻失效。
2. **reader 必须抄一份引用到自己名下。** 引擎 compaction 时会从自己的
   `_readers` 里 `pop` 掉旧文件；如果快照存的是同一个 dict，
   它就会跟着"丢文件"，读到一半突然 `KeyError` —— 而这恰恰是快照
   最该扛住的场景（边扫边归并）。
3. **`_file_ids` 是 pin 的依据。** `_apply_compaction()` 里对每个被删文件
   先查一下"有没有活快照引用它"：有就进 `_pending_delete`，**reader 不关、
   文件不删、缓存也不清**；没有才当场清理。

释放时反向做一遍：`_release_snapshot()` 重新算一次"还有哪些文件被引用"，
把已经没人要的待删文件真正删掉。

`demo.py` 第 16 节能直接看到：

```
--- 16. 快照的代价:文件被 pin 住,磁盘回收不了 ---
  归并前: 50 个文件,248.0 KiB
  开着快照做全量归并:
    pin 住 50 个文件,待删清单 50 个
    磁盘占用 491.2 KiB  ← 新旧两套同时存在
    快照仍然读得到: key00000 = xxxxxxxxxxxx...
  关掉快照之后:
    待删清单 0 个, 磁盘占用 243.1 KiB  ← 立刻回收
```

### `ScanCursor`：让 `scan()` 一调用就定格

```python
def scan(self, start=None, end=None) -> ScanCursor:
    snap = self.snapshot()                  # 立刻定格
    return ScanCursor(snap, snap.scan(start, end))
```

为什么必须"立刻"：调用方拿到迭代器的那一刻就认为它代表当前状态，
所以 `it = db.scan(); db.put(...)` 之后再迭代，**不该**看到那次写入。

那快照什么时候释放？交给迭代器：扫到底自动释放，中途 `break` 掉则由
对象回收兜底（`__del__`）。需要更精确的控制就直接 `with db.snapshot()`。

`engine.py` 里对应的维护动作：

```python
# 迭代器/快照关闭时
def _release_snapshot(self, snap):
    self._snapshots.pop(snap.snapshot_id, None)
    still_pinned = self._pinned_file_ids()
    for file_id in list(self._pending_delete):
        if file_id in still_pinned:
            continue                    # 还有别的快照在看它，继续等
        _meta, reader = self._pending_delete.pop(file_id)
        if reader is not None:
            reader.close()
        self._block_cache.evict_file(file_id)
        (self.data_dir / sstable_filename(file_id)).unlink(missing_ok=True)
```

### 读逻辑只留一份

`engine.get()` 和 `Snapshot.get_entry()` 走的是**同一个** `search_levels()`：

```python
def search_levels(levels, readers, key) -> tuple[bool, bytes | None, int]:
    for meta in levels[0]:                  # L0：范围重叠，只能挨个试
        ...
    for index in range(1, len(levels)):     # L1+：层内不重叠，二分定位
        ...
```

两边各写一份的话，迟早会有一边忘了检查布隆过滤器、或者忘了
"L0 要挨个试"—— 而这类分叉的表现是"偶发查不到数据"，极难定位。
同理 `find_file_in_level()` 被抽成模块级函数，好让快照能在
**自己捕获的那一份层结构**上做同样的二分（查找期间真实 manifest
可能已经被改掉了）。

## 并发写（阶段 6）

### 问题：一把锁同时保护两件代价差三个数量级的事

阶段 5 结束时，`put` / `delete` / `flush` / `compaction` 共用一把可重入锁。
问题是它们要保护的东西完全不成比例：

| 操作 | 临界区里在干什么 | 量级 |
|------|------------------|------|
| `put` | 追加几十字节到日志、改一个 dict 项 | 微秒 |
| `flush` | 编码一个几 MB 的文件、fsync、原子改名 | 几十毫秒 |
| `compaction` | 归并多个文件、再写一遍 | 几十到几百毫秒 |

用一把锁保护它们，等于**每次刷盘都把整个库停掉**。实测：刷一张 4 MiB
的内存表要 80 ms，这段时间里所有写和所有点查都在等。

### 做法一：拆成三把锁

```
_maintenance_lock ──► _append_lock ──► _state_lock     ← 顺序固定，不许反向
```

- **`_maintenance_lock`**：串行化刷盘和归并。它们都要改 manifest，
  而 manifest 是"整体原子替换"的 —— 两个维护操作同时改，
  后写的那个会把前一个的改动整个覆盖掉，文件就从清单里凭空消失。
- **`_append_lock`**：保护 **WAL 追加 + 内存表写入 + 内存表轮转** 这一组。
  这三件事必须成组原子，理由见下一节。
- **`_state_lock`**：manifest、readers、快照表、待删清单、计数器。
  它**绝不在磁盘 I/O 期间持有** —— 这一条就是"归并不卡读"的全部秘密。

### 做法二：不可变内存表 —— 刷盘时只换指针

光拆锁还不够。刷盘要把内存表的内容写成文件，而写入还在往里灌数据。
所以先把内存表"搬走"：

```
内存表写满
  → _append_lock 里换指针（微秒级）：
      满的那张 → 不可变内存表
      新建一张空表接住后续写入
  → 释放 _append_lock，其他写者立刻可以继续
  → 在锁外把不可变表慢慢写成 SSTable
  → 最后才更新 manifest、摘掉不可变表、重写 WAL
```

数据在写文件**之前**就已经从内存表里搬走了，所以写者不用等。

### 代价一：读路径多了一层

被轮转走的数据，既不在活动内存表里，也还不在 SSTable 里 ——
**它只在不可变内存表里**。漏掉这一层，表现就是"刷盘那一瞬间偶发查不到
刚写的数据"，而且只在恰好刷盘时才复现。

所以读路径变成：`活动内存表 → 不可变内存表 → L0 → L1 → L2……`
快照也一样：创建时把活动表和不可变表**合并**成一份有序列表
（同 key 活动表优先）。

`tests/test_concurrency.py` 里有两条测试专门盯着这个：
把刷盘卡在"正在写文件"那一刻，然后断言读和快照都必须看得到那条数据。
把不可变表那一层拆掉，它们会立刻失败。

### 代价二：刷完盘不能直接清空日志

单线程时 `flush()` 之后日志就可以清空 —— 里面的东西全在 SSTable 里了。
并发时不行：**日志里夹着新内存表的记录**，清空会把它们一起丢掉。

所以拆成两条路（`_rewrite_or_truncate_wal_locked`）：

| 当前内存表 | 做法 | 为什么 |
|------------|------|--------|
| 空 | `truncate()` | 日志里全是刚刷走的那张表，开销为 0。单线程顺序写入的常态 |
| 非空 | `rewrite()` | 用当前内存表的内容**整体替换**日志 |

`WAL.rewrite` 沿用"临时文件 + fsync + 原子改名"那套（和 SSTable、manifest
一模一样），所以崩在改名之前，旧日志仍然完好 —— 重放它是**幂等**的：
那些记录的値和 SSTable 里的一致。

顺带得到一个好处：**重写就是一次日志压实**。内存表里每个键只有一条记录，
而日志里同一个键可能被追加过很多次。所以并发写入时日志反而更小。

### 代价三：写入不能白等

刷盘的时候，别的写者发现内存表满了，会来抢 `_maintenance_lock`。
如果老老实实排队，就会排在一场"刷盘 + 最多 16 轮归并"后面 ——
实测 16 次维护里有 11 次是在**白等**，合计 2.7 秒。

但这些写者其实不需要等：它们的数据已经在 WAL 和内存表里了，
不会丢，也不需要立刻变成 SSTable。所以改成**抢不到就返回**：

```python
if self._maintenance_lock.acquire(blocking=False):
    try:
        self._drain_locked(force=False)
    finally:
        self._maintenance_lock.release()
    return
# 抢不到 → 直接返回。正在刷的那个人刷完会顺手再看一眼内存表
```

改完之后，维护等待的中位耗时从 **83 ms 降到 0 ms**，合计从 4098 ms
降到 1565 ms（同样 16 万次写入）。剩下的 1.5 秒全部落在
**真正执行刷盘+归并的那 5 个线程**身上 —— 那不是等待，是干活。

唯一的例外是内存表涨到 **两倍容量** 还没被刷出去：那说明写入比刷盘快，
再不等就要把内存撑爆，这时候才真的排队（背压）。纯 Python 的写入速度下
撞不到它。

### 收益实测

```
一、刷盘写文件的时候，一次 put 要等多久
   刷盘一次：4000 条，320 KiB，耗时 14.81 ms
   刷盘被钉住时连着写 300 次：中位延迟 0.00 ms

   阶段 5 的 put 会等        14.81 ms   ← 大锁被整个刷盘占着（推算下界）
   阶段 6 的 put 实际等       0.00 ms   ← 只碰 _append_lock

二、归并的时候，一次 get 要等多久
   归并 8 个文件耗时 21.56 ms
   阶段 5 的 get 会等        21.56 ms   ← 和归并抢同一把锁（推算下界）
   阶段 6 的 get 实际等       0.01 ms   ← 归并的 I/O 全程不持 _state_lock

四、默认配置下，写入会不会因为刷盘而停顿
   160,000 次 put，4 个线程，内存表 4 MiB（默认），总耗时 2557 ms
   期间刷盘 5 次，归并 6 次
     p50    0.00 ms
     p99    0.02 ms
     p99.9  0.08 ms
     max 1276.73 ms   ← 就是那 5 个「轮到自己刷盘」的线程
   超过 1 ms 的 put：5 次（0.0031%）
```

⚠️ **吞吐没有变好，而且不该指望它变好。** 实测 4 线程只有单线程的 0.56 倍 ——
但**完全不刷盘的基线也是 0.53 倍**，说明这是 CPython 的 GIL 造成的
（同一时刻只有一个线程在跑字节码），不是锁的设计问题。
阶段 6 买到的是**延迟隔离**，不是吞吐。

### 崩溃恢复需要改吗？不需要

这是这次改造里最让人意外的一点。日志里多出来的那一段（属于已经刷盘的
那张表）重放是幂等的 —— 值本来就一致。唯一要加的是启动时清掉
半截的 `wal.log.tmp`（和清理 `*.sst.tmp`、`MANIFEST.json.tmp` 一样）。

但**顺序**上多了一条硬约束：

> 不可变内存表只有在 manifest 已经指向它的 SSTable **之后**才能摘掉。

反过来的话，会出现一个瞬间：数据既不在内存里、也不在 manifest 里。
如果恰好在那一刻崩溃，而 WAL 又已经被重写过，数据就真丢了。
`_flush_immutable_locked` 里那两行注释说的就是这件事。

## 崩溃恢复

### WAL 尾部残缺

进程可能在**写记录的任意时刻**被杀死，日志末尾就会留下半条记录。

恢复策略只有一条规则：

> 从头顺序读，读到损坏就**截断到上一条完好记录**，保留之前的一切。

绝不能因为末尾几个坏字节就把整个日志判死刑。

`WAL.recover()` 会重放日志并把文件**真的**截断到有效边界，
所以函数返回后，日志里每个字节都是可解析的有效数据。

实际跑出来的效果（`python demo.py`）：

```
--- 12. 崩溃恢复:WAL 尾部残缺 ---
  WAL 从 85 字节被砍到 78 字节
  user:01 = alice
  user:02 = bob
  user:03 = None  (半截记录,被丢弃)
  启动恢复:重放 2 条记录(含截断)
  截断原因: payload 不完整:期望 21 字节,实际 14 字节(偏移 56)
```

### 启动时的清理与校验

```
1. 删掉所有 *.sst.tmp 和 MANIFEST.json.tmp   ← 崩溃留下的半截文件
2. 有 manifest? 读它。没有? 扫目录,把 .sst 全当 L0（阶段 2 的老目录）
3. 校验 manifest 引用的文件**都还在**        ← 缺一个就拒绝启动
4. 删掉 manifest 没引用的 .sst（孤儿文件）
5. 打开所有被引用的文件                       ← 损坏就拒绝启动
```

第 3 步和第 5 步都选择**拒绝启动**而不是"跳过坏文件继续跑" ——
因为那样"查不到"和"数据坏了"就没法区分了，静默丢数据比启动失败糟糕得多。

### 刷盘时的步骤顺序

`flush()` 里**顺序是唯一重要的东西**：

```
1. 把内存表快照写成 SSTable 并 fsync   ← 数据先落到新地方
2. 原子改名成正式文件
3. 更新 MANIFEST 并 fsync              ← 从这一刻起，新文件生效
4. 换掉内存里的 reader
5. 换一个空的内存表
6. 截断 WAL                            ← 最后才丢弃旧地方
```

任何一步之后崩溃都是安全的：只要 WAL 还在，重放一遍就能重建内存表。
重放是**幂等**的 —— 同样的 put 应用两次，结果一样。

## 八条必须遵守的规则

**1. 先写日志，再改内存**

```python
def put(self, key, value):
    self._wal.append(RecordType.PUT, kb, vb)   # ① 先落盘
    self._memtable.put(kb, vb)                 # ② 再改内存
```

顺序反了的话，"日志还没写完就崩溃"的场景下，内存里的改动会丢失，
而调用方已经收到"写成功"了 —— 这直接违反持久性。

**2. 删除必须留墓碑，而且墓碑要能跨层压制**

删除不能真的把键从表里抹掉。因为**更旧的版本可能躺在某个 SSTable 里**，
抹掉墓碑之后，那个旧值就会"复活"。

所以 `get()` 遇到墓碑时返回 `(True, None)`，而不是 `(False, None)` ——
`True` 表示"我确定这个键被删了"，于是**停止**往更旧的文件里找。

这是最容易写错、后果最严重的地方。阶段 3 又多了一层风险：
compaction 会重写文件，**丢墓碑的时机错了同样会让键复活**。
测试里专门有一组盯着这个（见下）。

**3. 删除不存在的键也要写墓碑**

听起来反直觉，但同样是因为"旧版本可能躺在磁盘上"。
如果跳过墓碑，那次删除就丢了。

**4. 过滤器永远不能有假阴性**

```
might_contain(k) is False  →  一定不在，可以放心跳过这个文件
might_contain(k) is True   →  可能在，还得真去读
```

这个不对称是**故意的**，而且不能反过来：

| | 后果 |
|---|---|
| 假阳性（说在、其实不在） | 白读一次文件 —— 慢一点，结果正确 |
| 假阴性（说不在、其实在） | **静默丢数据** —— 不报错、不崩溃，数据就是"没了" |

所以所有取舍都倒向"宁可说在"：

- 过滤器**损坏**时降级成"没有过滤器"（恒返回 `True`），而不是拒绝启动
- 文件**没有**过滤器时（v1 老文件）恒返回 `True`
- 引擎在 `might_contain` 外面包一层 `try/except` —— 真出了意外，
  退回"老实去读"，绝不因为一个优化结构而丢数据

反过来说，**墓碑也要进过滤器**。墓碑占着一个 key 位置，查询时同样需要
"确定不在"这个判断 —— 漏掉的话，查一个被删的键会白读文件。

**5. 被快照 pin 住的文件不能删，连 reader 都不能关**

阶段 3 的规则是"manifest 不再引用就删"。阶段 5 给它加了一个前提：

```
manifest 不再引用  →  还要看有没有活快照引用它
                        有  →  进待删清单，reader 保持打开，缓存也不清
                        没有 →  关 reader、清缓存、unlink
```

顺序也不能反：**先关 reader 再 unlink**。在 Windows 上句柄还开着时
`unlink` 会直接失败；而在 Linux 上会"删成功但数据还在"，于是快照
读到一半文件突然消失 —— 后者更糟，因为它不报错。

这条规则还有两个容易漏的分支，模糊测试专门盯着：

- **最后一个快照关闭时**必须回收待删文件（漏了 = 磁盘只涨不落）
- **引擎关闭时**必须把待删文件清干净（此时没有"还在读"的可能了）

**6. 迭代期间不持锁，靠 pin 而不是靠锁**

"读不阻塞写"和"读到的数据一定还在"这两件事，在阶段 5 是靠**两个不同机制**
分别保证的：

| | 靠什么 |
|---|---|
| 数据还在（文件不被删） | 快照 pin 住文件 → compaction 只能推迟删除 |
| 读不阻塞写 | 迭代全程不持有引擎锁 |

把它们混在一起（比如"用锁保护整个迭代过程"）会同时丢掉两个好处。
`tools/bench_stage5.py` 里直接探测了锁是否空闲（阶段 6 之后是三把锁一起探）：

```
空闲时三把锁都可用: 是
扫描中三把锁都可用: 是
```

**7. WAL 追加和内存表写入必须是一个原子步骤**

单线程时这条是废话 —— 反正也没别人。多线程时它是**唯一**保证
"重启前后数据一致"的东西：

```python
with self._append_lock:
    self._wal.append(rec_type, kb, vb)      # 日志顺序
    self._memtable.put(kb, vb)              # 内存表顺序
```

如果两者能被拆开，就可能出现"A 先追加日志、B 先改内存表"。
于是**重放日志得到的状态和崩溃前内存里的状态不一样** ——
同一个键最终值对不上。而这个差异只在"恰好崩在那一次"时暴露，
平时怎么测都测不出来。

`tests/test_concurrency.py::test_same_key_final_value_survives_restart`
就是盯这个的：多个线程反复覆盖同一个键，然后关掉重开，
断言读到的值和关闭前一致。

**8. 不可变内存表只能在 manifest 指向它的 SSTable 之后才能摘掉**

顺序错了会造出一个危险的瞬间：

```
❌ 先摘不可变表 → 再更新 manifest
   这一瞬间：数据不在内存里、也不在 manifest 里。
   此刻崩溃 + WAL 已经被重写过 = 数据真的没了。

✅ 先更新 manifest → 再摘不可变表
   这一瞬间：数据在内存里、也在 manifest 里。重复但安全。
```

这是"manifest 是唯一的有效文件集合"这条总原则在并发下的延伸：
**新的一套先就位，旧的一套才能退场**。

## 内存表（MemTable）

LSM 里唯一**可写**的数据结构。所有写入先落到这里，攒够了再整体刷成
不可变的 SSTable。

**为什么强调"有序"？** 刷盘时希望写出的 SSTable 内部有序 ——
这样查询才能二分查找，范围扫描才能顺序读。实现上用 `dict` 存储 +
遍历时 `sorted()`，兼顾 O(1) 查找和有序输出。

**墓碑用 `None` 表示。** 于是 `get()` 返回 `None` 有两种含义：
键不存在，或者键已被删除。对调用方而言这是同一件事。
需要区分时用 `get_entry()`：

```python
mt.put(b"alive", b"v")
mt.put(b"dead", b"v")
mt.delete(b"dead")

mt.get_entry(b"alive")     # (True, b'v')
mt.get_entry(b"dead")      # (True, None)   ← 墓碑
mt.get_entry(b"never")     # (False, None)  ← 从未出现
```

顺带一个容易忽略的推论：**同一代内存表里 put 完又 delete 同一个键，
只会留下一条墓碑** —— 内存表是个 map，旧值被直接覆盖，
刷盘时不可能把已经作废的值写出去。

容量是**估算**的，每条记录按 `len(key) + 64 + len(value)` 计费
（那 64 字节是 Python dict 的哈希槽和对象头开销）。不精确，
但足够用来判断"该刷盘了"。

## 归并迭代器

一个 key 可能同时存在于内存表和好几个 SSTable 里。`MergingIterator`
让"多个来源"对上层看起来像"一个有序表" —— 扫描和 compaction
都靠它，不用各自写一遍合并逻辑。

契约有三条：

1. 每个来源产出 `(key, value)`，按 key 升序
2. `value is None` 表示墓碑
3. **来源的先后顺序就是新旧顺序**：下标 0 最新

实现是标准 k 路归并，堆元素是 `(key, source_index, seq, value)`。
那个 `seq` 序号不是装饰：`bytes` 和 `None` 没法比大小，一旦堆比较
走到 value 上就会抛 `TypeError`。同 key 且同来源下标时靠 `seq` 决胜，
彻底避免比较 value。

墓碑会被**照常产出** —— 过滤是调用方的事。面向用户的 `scan()` 跳过它们，
但 compaction 必须看到，否则"删除"这个信息就丢了。

compaction 时 `inputs` 的顺序（`source_files + target_files`，都是新到旧）
**直接决定同 key 取谁** —— 排错了会读到旧值。所以这个顺序在
`CompactionTask.inputs` 里被固定下来，并单独测了。

### 并发测试怎么做到不碰运气

并发测试最容易写成"大部分时候能过"。`test_concurrency.py` 的做法是
**用事件把时序钉死**，而不是 `sleep` 一段时间去赌窗口：

```python
class BlockingWriter(sstable_mod.SSTableWriter):
    def finish(self):
        entered.set()            # 通知测试：刷盘已经进到"写文件"这一步了
        release.wait(timeout=30)  # 等测试放行
        return super().finish()
```

于是"刷盘进行中"这个时刻是**确定的**，可以在里面断言：
写入必须立刻成功、读必须看得到不可变表里的数据、快照必须看得到。

这类测试还做了一轮**变异验证** —— 故意把代码改坏，确认测试真的会失败：

| 把什么改坏 | 哪个测试失败 |
|------------|--------------|
| 读路径不查不可变内存表 | `test_read_sees_immutable_memtable` |
| 快照不合并不可变内存表 | `test_snapshot_sees_immutable_memtable` |
| 写入改回"排队等维护" | `test_writer_does_not_queue_behind_maintenance`（会挂死到超时）|

不做这一步的话，"测试全绿"可能只是因为它根本没在测那件事。

### 随机压力测试

单元测试只能覆盖我**想到**的情况。`tools/fuzz_compaction.py` 用固定种子的
随机操作序列去撞我没想到的：同一个键被反复改写、删了又写、写到一半触发归并、
随时重启 —— 每一步都和"如果只用内存里的字典"应该得到的结果对照。

阶段 4 之后它多查了四件事：

- 点查、全量扫描是否和模型一致
- manifest 的层序不变量
- **缓存不能超容量，也不能留着已被删文件的块**（漏掉 `evict_file` 的信号）
- **过滤器不能有假阴性** —— 挨个文件翻出它实际有的键，逐个问过滤器

阶段 5 又加了三类：

- **快照一致视图** —— 每开一个快照就把当时的模型**抄一份冻结起来**，
  之后每次检查都拿快照去比那份冻结的模型（而不是当前模型）。
  同时比全量扫描、点查、以及一个随机区间扫描。
- **pin 与延迟删除** —— 快照 pin 的文件必须都还在磁盘上；
  待删清单不能和 manifest 交叉；**没有快照时待删清单必须是空的**。
- **`ScanCursor` 的定格语义** —— 创建迭代器之后立刻写数据，迭代结果
  必须还是创建那一刻的状态。

参数也是每轮随机挑：过滤器 `0 / 4 / 10 / 16` bit/key、缓存
`0 / 512 B / 4 KiB / 1 MiB`。关掉过滤器和把缓存压到 512 字节这两条
极端路径，正确性要求和默认配置完全一样。

```

seed=  3 OK  存活键=31  文件=1  刷盘=64  归并=37  分层=[0, 0, 1]  过滤器=4bit/key 挡下=510  缓存=512B
```

### 预言机：拿"慢但显然正确"的实现校验"快但容易写错"的实现

模糊测试解决的是"我没想到的情况"。还有一类问题它解决不了：
**某个优化实现本身在边界上写错了，而错误恰好落在随机数据覆盖不到的地方。**

阶段 5 的 `Snapshot._memtable_source()` 就是这种代码 —— 用 `bisect_left`
在键列表上切区间，快，但四个边界（start 比第一个键还小、end 落在两个键之间、
`start == end`、反向区间）每一个都可能差一位。

所以 `MemTable.range_items()` 被**特意保留**下来：它先 `sorted()` 整张表
再从第一个键走，O(n)，慢得没法用，但**正确性一眼可见**。
它现在的工作是当**预言机（oracle）**：

```python
# tests/test_snapshot.py::TestMemtableSliceOracle
got  = dict(snap.scan(lo, hi))                       # bisect 版本（被测）
want = {k: v for k, v in model.range_items(lo, hi)   # 朴素版本（预言机）
        if v is not None}
self.assertEqual(got, want)
```

400 多个随机区间跑下来，只要 bisect 版本有一位偏差就会立刻暴露。

**这个模式值得复用**：任何时候你把一段"显然正确但慢"的代码换成
"快但需要动脑"的代码，别把旧的删掉 —— 留着当预言机。
手写边界用例只能覆盖你想到的边界，预言机覆盖你想不到的。

> 我验证过它不是白跑的：故意把 `bisect_left` 改成 `bisect_right`
> 注入一位偏差，6 个用例里 5 个立刻失败。

## 踩过的坑

**读块之前必须先校验长度。** 最早的 `_read_block` 是先 `read(length)`
再检查"读到的够不够"。测试用一个 1 TiB 的长度去打它，结果不是抛出
`CorruptionError`，而是 `MemoryError` —— 因为 `read(1 << 40)` 会先尝试
分配 1 TiB 内存，进程当场就没了。

这不是理论问题：块长度最终来自磁盘上的索引，损坏的数据可以让它变成
任何数字。**先核对边界，再申请内存。**

顺带也发现了一个好性质：索引块整体有 CRC，所以被篡改的索引会在
**打开阶段**就被拦住，伪造的块偏移根本没有机会被使用。
`_read_block` 里的长度校验于是成了纵深防御的第二道。

**空目录不该写 manifest。** 最早的 `_migrate_from_directory_scan()`
无论有没有扫到文件都会调用 `_save_manifest()`，于是"打开一个空目录"
这个动作会留下一个空 manifest。

看起来无害，但它等于把目录**占**下了：之后如果有人往这个目录里放一批
`.sst`（比如从阶段 2 的目录拷过来），下次启动会因为 manifest 已存在
而跳过扫描，把这些文件当成"孤儿"**删掉** —— 静默丢数据。

修法是：文件数为 0 时不写 manifest，目录保持"未初始化"状态，
每次启动都重扫一遍。测试 `test_files_dropped_into_fresh_directory_are_adopted`
就是从这个 bug 来的。

**我的测试断言算错过两次。** 一次是以为"墓碑被清掉后磁盘上少 1 条记录"，
实际上是少 2 条（墓碑 + 被它压住的旧值）；一次是以为"空目录打开后没有
manifest"，实际上有（就是上面那个 bug）。

两次都值得记一下，因为它们的处理方式一样：**先判断到底是实现错了
还是测试的假设错了**，然后把正确的语义固化成测试，而不是把断言改成
"能让它过"的样子。

**过滤器用内置 `hash()` 会在重启后"丢掉"全部数据。** 这是阶段 4 最隐蔽的坑：
`hash()` 每个进程的盐都不同，而过滤器是要落盘的。写进去的位图和重启后
查出来的位置对不上 → 所有存在的键都变成假阴性。**假阴性不是"慢"，
是"数据没了"**，而且不报错、不崩溃。

修法是换成 `hashlib.blake2b`。这个坑的价值在于它无法靠"跑一遍测试"
发现 —— 单进程测试里 `hash()` 完全正常。必须用子进程 + 不同的
`PYTHONHASHSEED` 才能钉住。

**我写错了一条模糊测试的不变量，还以为是真 bug。** 最初我在 fuzz 里
这样断言："如果某个 key 落在文件的 `[最小键, 最大键]` 范围内、而且它
确实存在，那过滤器就不能说它不在。" 结果第一轮就报假阴性，吓一跳。

查下来是我的假设错了：**文件的范围中间是可以有空档的**。一个 L0 文件
的范围可能是 `key003 .. key038`，但它只有 10 个键 —— 内存表里本来
就没攒到 `key032`。过滤器说"不在这个文件"是**完全正确**的，
`key032` 存在于别的文件里。

改成"拿文件里**实际**有的键去问过滤器"之后，不变量才是精确的。

> 顺带一个教训：`tools/bench_stage4.py` 里也能看到同一件事的另一面 ——
> 顺序写入时每个文件的键范围很窄，"范围检查"这个**免费**的过滤就已经
> 挡掉了大部分文件，布隆过滤器的收益看起来只有 86%；换成随机写序
> （每个文件都覆盖全域）才显出 99%。**不设计对场景，就量不出真实收益。**

**快照不能直接存引擎那个 `_readers` dict。** 这是阶段 5 最隐蔽的一处。
第一版 `Snapshot.__init__` 里写的是 `self._readers = readers`，
把引擎的字典直接存了下来 —— 看起来毫无问题，因为那一刻两者内容确实一样。

但 compaction 会 `self._readers.pop(meta.file_id)`。存的是同一个 dict，
快照就跟着"丢文件"，读到一半突然 `KeyError`。而这恰恰是快照最该扛住的
场景：**边扫边归并**。

修法是抄一份引用到自己名下：

```python
self._file_ids = frozenset(m.file_id for level in self._levels for m in level)
self._readers = {fid: readers[fid] for fid in self._file_ids}
```

模糊测试里也补了一条不变量盯着它：`set(snap._readers) == set(snap.file_ids)`。

**基准测试的对照组不能用同一个目录。** `bench_stage5.py` 第一版里，
"没有快照"和"有快照"两组测的是同一个数据目录：第一组跑完 `compact_all()`
之后，库已经被压成"一个文件、位于最底层"的**最理想状态**；
第二组再调 `compact_all()` 会直接返回"无事可做"，于是 pin 住 0 个文件、
多占 0 字节 —— 整段结论全是 0，而且看起来"很正常"。

基准测试里这类错误比单元测试更危险：它不会失败，只会**安静地给出
一个假结论**。所以现在用两个独立目录，并且在打印前 `assert` 快照
确实读得到数据。

**我在阶段 5 又算错了一次断言（第三次了）。** 写
`test_end_is_exclusive` 时，我以为"区间是 `[start, end)`，所以
`files_overlapping(files, b"c", b"d")` 应该一个文件都不选"。实际上
文件 `a..c` 的**最大键就是 `c`**，而 `c` 确实在 `[c, d)` 里 ——
它必须被选中。真正体现"右开"的是那个**最小键恰好等于 `end`** 的文件。

同一个坑还让我把 `test_scan_freezes_at_call_time` 的期望写反了：
`db.scan()` 之后再 `db.delete("a")`，我却断言迭代结果是空的 ——
而"定格"的意思恰恰是它**还看得到 `a`**。

三次都值得记一下，因为处理方式一样：**先判断到底是实现错了还是测试的
假设错了**，然后把正确的语义固化成测试，而不是把断言改成"能让它过"的样子。

**并发吞吐掉到 0.55x —— 差点把 GIL 的账算到自己头上。** 阶段 6 的基准
第一版跑出来：1 线程 46,000 条/秒，4 线程 25,000 条/秒。看起来像是
"拆锁把性能拆坏了"。但加上一组**完全不刷盘、不归并**的对照组就露馅了 ——
那一组也掉到 0.58x，而它根本没走任何锁竞争路径。

所以结论是：纯 Python 多线程写**不可能**快过单线程，这是 GIL 决定的
（同一时刻只有一个线程在跑字节码，多出来的线程只是增加切换开销）。
阶段 6 买到的是延迟隔离，不是吞吐。**没有对照组的话，这个数字会被
当成设计缺陷**，然后去优化一个不存在的问题。

**"不排队"和"排队"，差 2.7 秒。** 第一版 `_after_write` 是老老实实
抢 `_maintenance_lock`（阻塞式）。看起来更"稳妥"，实际是把一堆写者
排在一场"刷盘 + 最多 16 轮归并"后面。加了个计数器一量：16 次维护调用里
**11 次是在纯等**，合计 4098 ms。

改成"抢不到就直接返回"之后，维护等待的中位耗时 83 ms → 0 ms，
合计 4098 ms → 1565 ms。而且**这个改动不需要引入任何新机制** ——
那些写者的数据本来就已经在 WAL 和内存表里了，等的那一下纯粹是白等。

教训：加锁的时候容易默认"排队更安全"，但先问一句
**"我等的那个东西，是不是本来就已经安全了？"**

**"测试全绿"和"测试有效"是两回事。** 写完并发测试之后，
我故意把代码改坏了三次（读路径不查不可变表、快照不合并不可变表、
写入改回排队），确认对应的测试真的会失败 —— 第三个甚至会挂死到超时。
不做这一步的话，那 12 个用例可能只是"恰好都通过了"，
而它们本该盯住的那条路径其实没被走到。

### 现在的能力边界

**并发相关的边界（阶段 6 新增）：**

- **没有后台维护线程**：刷盘和归并是"谁触发谁执行"。所以那一次 `put`
  要付全部成本 —— 实测最坏情况下要 1.2 秒（刷一张 4 MiB 的内存表
  + 6 轮归并）。**别的线程不受影响**（等待的中位耗时是 0），
  但触发维护的那个线程会卡住。要压掉这条尾巴就得把维护挪到独立线程上，
  那是另一件事（还要处理线程生命周期、关闭时序、错误传递）。
- **写入仍然会排队，但只在极端情况下**：内存表涨到两倍容量还没被刷出去时，
  写入必须等（背压）。这是对的 —— 不等就会把内存撑爆。
  但在纯 Python 的写入速度下（几 MB/s）基本撞不到：实测 16 万次并发写入里
  只有 5 次超过 1 ms。
- **多线程吞吐不会变好**：CPython 的 GIL 决定了纯 Python 多线程写
  不可能快过单线程（实测 4 线程只有单线程的 0.56 倍）。
  阶段 6 买到的是**延迟隔离**，不是吞吐。这一点用"完全不刷盘的基线"
  单独对照过，免得把这个锅算到锁的设计上。
- **只支持"一个不可变内存表"**：不可变表只有一个槽位。真实引擎会排一个
  队列（`max_write_buffer_number`），让刷盘慢的时候写入还能继续轮转。
  这里只有一张，所以刷盘期间内存表满了就只能等下一次轮转。

**一直存在的边界：**

- **没有 per-key 版本链**：快照是"抄一份结构 + pin 一批文件"，
  所以只能读**"我自己创建那一刻"**，不能读"历史某个时间点"。
  想做后者就得给每条记录编号（`(key, seq)`），磁盘格式要改。
- **快照会占住磁盘**：只要还有一个快照活着，被它 pin 的旧文件就删不掉。
  长事务型的用法（开着快照跑几小时）在真实引擎里要靠
  "最长快照时间"来兜底触发 compaction，这里没有。
- **没有事务**：`put_many` 中途失败会留下部分写入，也没有原子批量写。
- **过滤器只加速点查，不加速范围扫描**：`scan()` 要读所有重叠文件的所有块，
  过滤器帮不上忙。真实引擎会用它做前缀扫描的剪枝。
- **没有分区索引（partitioned index）**：索引块整体常驻内存。
  现在每个文件的索引只有几百字节，够用；文件大到索引装不进内存时，
  就得把索引也切成块按需加载。
- **缓存没有优先级**：热点数据和冷数据一视同仁地被 LRU 对待。
  RocksDB 用高优先级池 + 布隆过滤器/索引也占缓存，这里都没做。
- 每个 SSTable 常驻一个文件句柄，文件多了会吃掉句柄数
- `level_budget` 只按字节算，不看文件数、不看删除比例；
  真实引擎还会考虑文件年龄、墓碑占比等
- **读路径仍然要短暂持 `_state_lock`**：点查在锁里做磁盘 I/O。
  它不会被归并卡住（归并的 I/O 在锁外），但多个点查之间还是会互相串行。
  要彻底解决得让读也走 pin（像 `scan()` 那样），代价是每次点查都要
  建一个快照对象。

## 设计取舍

**为什么 WAL 默认不 fsync？**

`sync_on_write=False` 时能扛住**进程崩溃**（数据在 OS 页缓存里，
进程死了但内核还在），但断电可能丢最近几条。`True` 才扛得住断电，
但慢一个数量级。默认选 False 是因为大多数场景下"进程崩溃不丢数据"
已经够了，断电保护可以按需开启：

```python
db = LSMEngine("./data", wal_sync_on_write=True)
```

**为什么关引擎时不自动刷盘？**

那样每次关闭都会留下一个很小的 SSTable。内存表的数据由 WAL 保证，
下次启动重放即可 —— 让"关闭"保持廉价。

**为什么 manifest 每次重写整个文件，而不是追加式日志？**

状态只有几 KB，重写的代价可以忽略，而"整体替换"的正确性显然更容易论证。
RocksDB 用追加式是因为它的 manifest 会涨到几 MB，且需要支持并发读快照 ——
这些约束在 mini-lsm 里都不存在。

**为什么布隆过滤器是每文件一个，而不是全局一个？**

全局一个过滤器只能回答"这个 key 在整个库里存不存在"。但查询需要的是
更细的粒度："这个 key 在**这个文件**里存不存在" —— 只有这样才知道
该跳过哪个文件。所以过滤器必须跟着文件走，跟文件的键范围一一对应。

**为什么块缓存缓存的是"解析后的记录列表"而不是原始字节？**

因为纯 Python 里贵的是**解析**，不是 `read()`。原始字节读回来还得
逐条 `struct.unpack`，缓存字节等于只省掉一半。而 SSTable 是不可变的，
解析结果永远不会变 —— 直接存下来，命中时省掉整条"读盘 + 校验 + 解析"路径。

**为什么用 `OrderedDict` 而不是自己写双向链表？**

`move_to_end` 和 `popitem(last=False)` 都是 O(1)，标准库已经写好了。
自己写链表要多几十行、多两处指针操作出错的机会，换来的只是省一个 dict 的开销。

**为什么缓存的值要连大小一起存？**

淘汰时需要知道"删掉它能腾出多少字节"。如果值只存记录列表，
每次淘汰都要把列表重新遍历一遍算大小 —— 淘汰是 O(n) 的，
而它发生在**每次 put** 的路径上。存成 `(大小, 记录列表)` 之后淘汰是 O(1)。

**为什么 compaction 的策略要单独一个模块？**

因为策略的边界条件特别多（哪一层该动、要不要带上重叠文件、能不能丢墓碑），
而这些判断如果混在"写文件 + 改 manifest + 删文件"的机制代码里，
就只能靠真的造数据来测。分开之后，42 个策略测试全部在内存里跑完，
总共 0.001 秒。

**为什么快照要用"抄结构 + pin 文件"，而不是引用计数 + 全局序号？**

引用计数（每条记录一个 `seq`）能支持"读任意历史时间点"，但要求
磁盘格式里带序号 —— WAL 和 SSTable 的 entry 都要加字段，还要兼容老文件。
而"抄结构 + pin"一个字节都不用改，代价是只能读"我自己创建那一刻"。

对这个项目的目标（把 LSM 的每一层讲清楚）来说，后者的性价比高得多：
它把"一致视图"这件事的**本质**暴露出来了 ——
一致视图 = 不可变数据 + 冻结的元数据 + 防止回收的引用。
真实引擎上 MVCC 是为了更细的粒度（读任意时间点、不阻塞 compaction），
但那是在这个基础上再加东西。

**为什么 `engine.scan()` 返回的是一个 `ScanCursor` 而不是裸生成器？**

因为"一调用就定格"和"快照必须释放"这两条要求互相拉扯：

- 要定格 → 快照必须在 `scan()` 里**立刻**创建
- 要释放 → 得快照有个明确的归属

交给迭代器正好：迭代到底自动释放，中途 `break` 掉靠 `__del__` 兜底，
需要精确控制就自己 `with db.snapshot()`。裸生成器做不到这点 ——
它没法在"被丢弃"时可靠地触发清理。

**为什么 pin 住的文件连缓存块都不清？**

因为快照还要读它。清掉不会读到脏数据（`file_id` 不复用），
但快照下次读它时得重新走一遍磁盘。留在缓存里正好还能命中。
真正删文件的时候再 `evict_file` —— 那时才确定没人要了。

**为什么 `Snapshot` 只持引擎的弱引用？**

引擎强引用快照（登记在 `_snapshots` 里），快照弱引用引擎。
单向强引用，两者之间没有循环，于是快照的释放时机完全由调用方
（或 GC）决定，不会被引擎拖着不放。

反过来的话，一个被 `del` 掉的快照会一直挂在引擎的 `_snapshots` 里，
把它 pin 的文件永久占住 —— 而且没有任何报错。

**为什么写句柄延迟打开？**

`WAL.__init__` 不创建文件、不占句柄，只有真正 `append` 时才打开。
因为"只想重放看看日志里有什么"是很常见的用法（`read_records`、
诊断工具），构造时就打开写句柄会让这种用法泄漏文件句柄。

**为什么异常要分层？**

```
LSMError
├── InvalidArgumentError    用法错误 —— 直接报给用户，不该重试
├── ClosedError             对已关闭的引擎操作
└── CorruptionError         数据损坏 —— 恢复路径上应被捕获并截断
    ├── TruncatedRecordError      写入中途崩溃留下的残骸（预期内）
    └── ChecksumMismatchError     磁盘数据被改写或位翻转
```

让调用方能精确区分"数据坏了"（截断恢复）和"你用法错了"（直接报错），
而不是笼统地 `except Exception`。
